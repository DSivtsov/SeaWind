# ADR 0021 — Create CI & CD for develop & TST

## 1. Причина решения

Проект WorkshopCode требует автоматизированного процесса проверки качества кода при работе с Pull Request в ветку `develop`, а также автоматической сборки и публикации Docker-образа API при обновлении этой ветки.
Цель — обеспечить минимальный, но стабильный DevOps-контур:

* ранняя проверка качества кода перед merge;
* воспроизводимая сборка образа;
* автоматический деплой на окружение **TST**, которое используется для тестирования функционала до попадания в другие среды.

Для реализации используются GitHub Actions.

## 2. Описание решения
Используются две отдельные автоматизации:

### **1. CI для Pull Request в develop**
Назначение: дать быструю обратную связь по качеству изменений до merge.

Файл: **ci-pr-develop.yml** (`.github\workflows`)
Запускается при создании, обновлении или переоткрытии **PR** в ветку `develop`.

**CI** выполняет действия в соответствии с разделом "*3. Обязательная Сборка и Тестирование в режиме Release через dotnet*" документа [WorkshopCode_ProjectRun](https://github.com/DSivtsov/SeaWind/wiki/WorkshopCode_ProjectRun)
* получение репозитория;
* сборку .NET решения с использованием общей composite-action (*build-dotnet*);
* запуск тестов (кроме интеграционных, требующих спец-окружения);
* публикацию результатов тестов и Postgres-лога как артефактов.

❗ Примечание. Все тесты, использующие тестовую PostgreSQL-БД, и которые должны находиться в **namespace** `Api.UnitTests.IntegrationTestDB` автоматически исключаются из **CI** при помощи фильтрации по этому namespace (так как они не совместимы с **CI** и приводят к ошибкам запуска)

### **2. CD для ветки develop → деплой в TST**
Назначение: автоматическая поставка обновлённого API-сервиса на окружение TST.

Файл: **cd-develop-tst.yml** (`.github\workflows`)
Запускается автоматически при пуше изменений в ветку `develop`, который производится после согласования **PR**

CD выполняет:
* сборку решения через общую action;
* запуск тестов и сбор покрытия;
* генерацию HTML Coverage Report;
* публикацию отчётов (тесты, Postgres-лог и Coverage Report) как артефактов;
* сборку Docker-образа (`./docker/Api.Dockerfile`);
* публикацию образа в GitHub Container Registry;
* маркировку образов тегами commit SHA и ветки;
* логирование успешного завершения.

ℹ Примечание.
- Также данный **workflow** можно запускать и в *ручном режиме*, если надо обновить окружения TST текущим кодом из `develop`.
- Относительно использования **HTML Coverage Report** см. документ: [Analize HTML Coverage Report](https://github.com/DSivtsov/SeaWind/wiki/Analize%20HTML%20Coverage%20Report)

ℹ Примечание. В связи с текущим отсутствием окружения TST дополнительные шаги, связанные с **Deploy to TST via SSH**, временно не выполняются:
* установка переменных окружения TST
* загрузка Docker-образа на сервер TST
* обновление и перезапуск контейнера TST
При перезапуске контейнера можно автоматически выполнить миграции и загрузку демо-данных.

### **3. Общая composite-action для сборки .NET**
Для устранения дублирования шагов сборки, общие действия вынесены в отдельный **action**
Файл: **action.yml** (`.github\actions\build-dotnet`)

**Action** выполняет:
* установка SDK по `global.json`;
* кэширование NuGet пакетов;
* очистка, restore и build в режиме **Release** с `warnaserror`.

## Примечание
Получить доступ к артефактам результатов выполнения тестов, как и к самим логам выполнения **workflow** можно в разделе репо [Actions](https://github.com/DSivtsov/SeaWind/actions)

## **Out of Scope**

* автоматизация деплоя на PROD / STG;
* стратегия катастрофоустойчивости и прогрева окружений;
* управление миграциями, сидированием и rollout-стратегиями;
* секрет-менеджмент вне GitHub Actions.
