# ADR-0034: BootstrapGuard

1.  В приложении есть два разных уровня контроля:
    *   **Bootstrap (целостность auth-состояния и готовность приложения)** — должен быть единым и строгим.
    *   **RouteGuard (доступ по URL и роль)** — решает только “пускать/не пускать” по маршруту.
2.  Ранее часть “невалидных” auth-состояний могла протекать в приложение и давать странные эффекты (пустые экраны/полу-авторизованные UI).
3.  По контракту Auth (`me`) может быть `loading/ready/error/empty`, но **некоторые комбинации недопустимы**, если `isAuthenticated === true`.
    ctx\_frontend\_mvp\_auth\_final\_v3

Решение
-------

### 1) Ввести BootstrapGuard как единую точку bootstrap-проверки

BootstrapGuard — верхнеуровневый guard, который проверяет:

1.  `apiHealth` (если используется в проекте как индикатор “API жив/не жив”).
2.  Все **невалидные** состояния `authCtx.me.kind` относительно `isAuthenticated`.

BootstrapGuard обязан **не пропускать дальше** приложение, если состояние невалидно.

### 2) Правила валидности (инварианты)

1.  Если `isAuthenticated === true`, то допустимы:
    *   `me.kind === "loading"` (пока грузим `/api/users/me`)
    *   `me.kind === "ready"`
2.  Если `isAuthenticated === true`, то **недопустимы**:
    *   `me.kind === "empty"` (т.к. `empty` по контракту означает “токена нет”)
    *   `me.kind === "error"` (это реальная проблема сети/5xx — нельзя продолжать как будто всё ок)

Эти правила следуют из модели `me` и общей схемы auth-решений.

ctx\_frontend\_mvp\_auth\_final\_v3

### 3) Поведение при невалидном состоянии

BootstrapGuard:

*   показывает “блокирующее” состояние (минимальный UI: текст/placeholder),
*   **не рендерит `<Outlet />`** и не пропускает ниже RouteGuard/страницы, пока состояние не станет валидным.

Примечание: BootstrapGuard не решает роли и URL-доступ — это задача RouteGuard.

ctx\_guard\_routes

### 4) Граница ответственности с RouteGuard

RouteGuard:

*   отвечает **только** за доступ по URL/ролям,
*   не обязан разбирать все варианты `me.kind`,
*   может возвращать `null` для “недостижимых” случаев, если они гарантированно перехватываются выше BootstrapGuard.
    ctx\_guard\_routes

Следствие / Инструкция по применению
------------------------------------

1.  BootstrapGuard ставится **выше** RouteGuard в дереве роутов/лейаутов (там, где он реально может “заблокировать” приложение).
2.  Все проверки `apiHealth` и “невалидных auth-состояний” концентрируются **только** в BootstrapGuard (не размазывать по страницам/лейаутам).
3.  RouteGuard остаётся простым и предсказуемым: URL + role-check, без попыток чинить auth.

Out of Scope
------------

1.  Ретрай-логика `apiHealth` и сложные сценарии восстановления сети.
2.  UI-полировка (красивые экраны ошибок/diagnostics).
3.  Расширение модели auth (refresh token, background polling и т.п.).
    ctx\_frontend\_mvp\_auth\_final\_v3
