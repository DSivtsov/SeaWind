## ADR 0020: Настройка хранения строковых окончаний в Git

**Дата:** 2025-11-30

### Почему

В проекте используются разные операционные системы (Windows / Linux), что приводит к рассинхронизации строковых окончаний (`CRLF` vs `LF`). Это приводит к появлению «мусорных» diff-ов (когда git отмечает, что изменения есть в файле, а реальных/существенных изменений нет), конфликтам, проблемам с билд-тулзами и форматтерами.
Цель — обеспечить единообразие: **в репозитории все текстовые файлы должны храниться только с LF**.

### Решение
#### Общие настройки для репозитория
1) В корне репозитория, в конце файла `.gitattributes` добавить fallback-правило:

```gitattributes
*          text=auto eol=lf
```
    📝 Примечание.

- «*» — все текстовые файлы, которые не попали под более конкретные правила выше
- `text=auto` — Git автоматически определяет текст/бинарный тип
- `eol=lf` — **хранение в репозитории только LF**

📌 Это правило **не ставим первым**, иначе оно затрет все остальные.

2) Нормализация текущих файлов:
Настройки локального Git и IDE рекомендуются, потому что Git управляет только тем, что попадает в репозиторий, а IDE сохраняет файлы на диск. Без настройки IDE новые файлы могут снова записываться в CRLF, что приводит к лишним diff’ам.
```bash
git add --renormalize .
git commit -m "Normalize line endings to LF"
```

---

#### Дополнительные локальные настройки для разработчиков
Настройки локального **Git** и **IDE** рекомендуются, потому что **Git** управляет только тем, что попадает в репозиторий, а **IDE** сохраняет файлы на диск. Без настройки **IDE** новые файлы могут снова записываться в CRLF, что приводит к лишним diff’ам.

1) Рекомендованные локальные настройки **Git** (ставятся только для текущего репозитория):

```bash
git config --local core.autocrlf false
git config --local core.eol lf
```

2) Рекомендации по настройке IDE
Даже при правильной конфигурации Git правила `.gitattributes` применяются только при операциях индексирования и checkout.
IDE же работают с файлами напрямую и могут сохранять их с CRLF по умолчанию, тем самым нарушая единообразие EOL в рабочей директории.
Поэтому требуется явная конфигурация форматирования в редакторах, чтобы гарантировать сохранение LF на уровне файловой системы.

#### Visual Studio / VS Code: `.editorconfig`

В корне репозитория:

```ini
root = true

[*]
end_of_line = lf
insert_final_newline = true
```

Назначение правил:

| Правило                       | Что делает                                                         |
| ----------------------------- | ------------------------------------------------------------------ |
| `root = true`                 | говорит IDE, что это главный файл настроек форматирования          |
| `end_of_line = lf`            | заставляет сохранять файлы с LF                                    |
| `insert_final_newline = true` | гарантирует перевод строки в конце файла → меньше конфликтов в Git |

📌 Это **главный источник истины** для любого редактора и CI, включая VS и VS Code.

### VS Code: User `settings.json` (глобально)
Чтобы новые файлы создавались сразу с LF и редактор не переопределял формат окончания строк локальными настройками пользователя.

Файл:

* **Windows** → `%APPDATA%\Code\User\settings.json`
* **Linux/Mac** → `$HOME/.config/Code/User/settings.json`

Рекомендуемый минимальный набор:

````jsonc
{
    "editor.useEditorConfig": true,
    "files.eol": "\n",
    "files.insertFinalNewline": true,
    "files.trimTrailingWhitespace": true
}
````

Смысл:

* `editor.useEditorConfig: true` — VS Code подчиняется `.editorconfig` (он важнее user-настроек);
* `files.eol: "\n"` — новые файлы по умолчанию с LF;
* `files.insertFinalNewline: true` — перевод строки в конце файла;
* `files.trimTrailingWhitespace: true` — удаление лишних пробелов/табов в конце строк.

    Если `.editorconfig` есть — **он всегда главнее** `settings.json`.
    `settings.json` здесь — только страховка и комфорт по умолчанию.

### Как проверить, что всё работает
#### 1. Проверка настроек репозитория
1. Финальная проверка

```bash
git grep -Il $'\r'
```
Вывод должен быть **пустой**, если есть какой то файл, то нужно проверить применяются ли к нему настройки `.gitattributes` (есть ли влияние)
Вот на примене на примере файла `src/backend/Api/Program.cs`
```bash
git check-attr --all -- src/backend/Api/Program.cs
```
    Ответ команды должен быть:
    src/backend/Api/Program.cs: text: auto
    src/backend/Api/Program.cs: eol: lf

    📝 Примечание. Если иначе наиболее вероятно `.gitattributes` создан в неправильной кодировки и git его не видит, надо пересоздать и повторить все предыдущие шаги.

#### 2. Проверка рабочей директории
1. Вначале удалить временные файлы
```bash
find . -type d \( -name bin -o -name obj \) -prune -exec rm -rf {} +
```
или
```powershell
Get-ChildItem -Recurse -Force -Directory bin,obj | Remove-Item -Recurse -Force
```

 2. Проверка рабочей директории (а не репозитория)
Цель: найти файлы в текущей рабочей папке, где ещё остался CRLF (редактор/IDE насрал), даже если репозиторий уже в LF.
Команда (из корня репо):
```bash
find . -type f \
  -not -path '*/.git/*' \
  -not -path '*/.vs/*' \
  -exec grep -Il $'\r' {} +

```
или
```powershell
Get-ChildItem -Recurse -File -Force |
    Where-Object {
        $_.FullName -notmatch '\\\.git\\' -and
        $_.FullName -notmatch '\\\.vs\\'
    } |
    Select-String "`r" -List |
    Select-Object -ExpandProperty Path
```

3. Очистка рабочей копии
Очистка рабочей копии делается **на той ветке, из которой ты хочешь получить “идеальное” состояние на диск**.
Если проверка рабочей директории (bash/PowerShell) показала файлы с `CRLF`, можно пересобрать рабочую копию из текущего коммита (`HEAD`) с учётом `.gitattributes`.

- Перейти на ветку, состояние которой нужно получить на диск (обычно `develop` или `main`), и убедиться, что все нужные изменения **закоммичены**:
```bash
git status
git checkout develop   # или другая целевая ветка
```
- Выполнить пересборку рабочей директории:
```bash
git rm --cached -r .
git reset --hard
```
делает:

* `git rm --cached -r .` — вычищает индекс (staging), но **файлы на диске не трогает**
* `git reset --hard` — затирает текущую рабочую директорию **состоянием текущего HEAD**
**HEAD = текущая ветка** (то, где ты сейчас стоишь: `develop`, `main`, `feature/xxx` и т.д.)

После этого рабочая директория будет полностью соответствовать текущему `HEAD` выбранной ветки, с применёнными правилами из `.gitattributes` (то есть с `LF`).



### Следствие

* Репозиторий гарантирует хранение только LF
* Устраняются ложные изменения в diff-ах
* Минимизируются конфликты при работе в команде
* Предотвращается повторное появление CRLF в истории
* Есть чёткий чек-лист по диагностике и исправлению проблем EOL

### Out of Scope

* Бинарные файлы (png, fbx, dll и т.п.)
* Настройки IDE и автоформатирования
