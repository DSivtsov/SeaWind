# ADR 0029: Frontend Authentication & Token Storage

## Почему / Контекст

В рамках Frontend MVP необходимо было определить:
- единый способ хранения токена аутентификации;
- поведение приложения при `401 / 403`;
- границу ответственности между UI, fetch-слоем и навигацией;
- UX-поведение без forced-login и без «сломанных» экранов.

Решение должно:
- соответствовать строгому MVP;
- не вводить преждевременные абстракции (refresh tokens, silent renew и т.п.);
- быть расширяемым в будущем (roles, guards), но не усложнять текущую реализацию.

---

## Решение

### Общие принципы (MVP)

- Refresh token **не используется**.
- JWT TTL фиксирован: **2 часа**.
- Forced-login модальные окна **не используются**.
- Пользователь **не блокируется** на текущем экране.
- При проблемах доступа используется UX-паттерн:
  **redirect `/courses` + информационное сообщение**.

---

### Хранение токена

- Используется **`localStorage`**.
- Токен также хранится в памяти (`AuthProvider`) как runtime‑источник истины для UI.
- `localStorage` используется для:
  - восстановления сессии при reload;
  - синхронизации logout между вкладками (через `storage` event).

Единый ключ токена определяется в `authStorage.ts`.

---

## Общая архитектура

### Общий контракт

- `401` — пользователь не аутентифицирован.
- `403` — пользователь аутентифицирован, но не имеет доступа.

### Поведение

1. Любой `401 / 403` перехватывается на уровне fetch-обёртки.
2. Генерируется событие потери доступа с указанием причины.
3. Auth-слой очищает токен и выполняет redirect:
   - `/courses`
4. Причина передаётся через `navigate state`.

Никаких forced-modal или автоматического открытия Login не используется.

---

## UX-поведение на `/courses`

- На `/courses` отображается **небольшое информационное модальное окно**.
- Сообщение показывается **один раз** после redirect.
- Тексты:
  - `unauthorized` → «Чтобы продолжить, войдите в систему»
  - `forbidden` → «У вас нет доступа к этому разделу»
- После закрытия модального окна пользователь остаётся на странице.

Login / Registration остаются **добровольным действием пользователя**.

---

### Архитектура решения

Решение построено с разделением ответственности по уровням:
обнаружение проблемы доступа, принятие решения и UX-реакция разделены между отдельными слоями, что исключает дублирование логики и упрощает расширение за пределами MVP.

Подробное описание подхода см. в документе:
**Описания подхода Frontend Auth v0 для реализации аутентификации**
Документ: [Frontend Auth v0 — описание подхода](../frontend/Frontend%20Auth%20v0.md)

**Уровни:**

* **`authStorage`** — хранение токена и рассылка события потери доступа.
* **`apiRequests`** — добавление токена к запросам, детект `401 / 403`.
* **`AuthProvider`** — очистка auth-состояния и redirect на `/courses`.
* **Layout / Pages** — отображение UX-сообщения, без auth-логики.

---

## Следствия / Инструкции по применению

- Страницы **не обрабатывают** `401 / 403` вручную.
- Auth‑логика **не дублируется** в UI‑компонентах.
- Любые новые API‑вызовы должны использовать `apiRequests`.
- Расширения (refresh token, role guards, silent renew) возможны,
  но **вынесены за рамки MVP** и требуют нового ADR.

---

## Out of Scope

- Refresh tokens.
- Silent renew.
- Forced-login UX.
- Role-based guards (будут оформлены отдельным ADR).
- Server-side session handling.
