# ADR 0024: Frontend–Backend API Interaction (MVP, No Refresh)
## Почему
В рамках MVP необходимо зафиксировать **единый и исчерпывающий контракт взаимодействия фронтенда и бекенда**:
- правила HTTP‑взаимодействия;
- обработку ошибок;
- retry‑поведение;
- модель загрузки страниц;
- ожидания от backend‑контрактов.
---

## Общие принципы (MVP)

- Используется **native fetch**.
- Обрабатывается только необходимый минимум состояний.
- Refresh‑токены **не используются**.
- `401` трактуется как **глобальное состояние сессии**, а не ошибка экрана.
- Всё, что связано с HTTP/transport, размещается в `shared/api`.
- Pages отвечают только за:
  - `uiState`,
  - данные,
  - отображение ошибки.

---

## Классификация ответов API

### Успех
- HTTP `200–299`.
- Тело ответа:
  - обычно `application/json`;
  - для списков — массив (`[]`, если данных нет).

### Ошибки

| Тип | Коды / примеры | Поведение фронтенда |
|----|----------------|---------------------|
| Auth | `401` | logout + auth‑flow |
| Client | `400 / 404 / 409 / 422` | сообщение пользователю |
| Server | `500 / 502 / 503 / 504` | `uiState = "error"` |
| Network | offline / timeout / CORS | `uiState = "error"` |
| Abort | `AbortController` | игнорируется |

---

## Чтение сообщения об ошибке

### Базовое правило
- Тело ответа можно прочитать **только один раз**.

### Алгоритм
1. Проверить `Content-Type`.
2. Если `application/json` или `application/problem+json`:
   - попытаться извлечь `detail / title / message`;
   - при ошибке парсинга — **не читать тело повторно**.
3. Если сообщение не получено — прочитать `res.text()` **один раз**.
4. Если тело пустое → `HTTP {status}`.

### Причина
`res.json()` и `res.text()` читают один и тот же stream. Повторное чтение приводит к ошибкам обработки.

---

## HTTP‑слой

### singleAttempt
Отвечает за **одну попытку запроса**:
- сбор заголовков (`Accept`, `Content-Type`, `Authorization`);
- выполнение `fetch`;
- обработку `!res.ok`;
- `204` → `undefined`;
- парсинг JSON;
- классификацию ошибок:
  - `abort`,
  - `network`,
  - `http`,
  - `parse`.

### apiRequest
- Оборачивает `singleAttempt`.
- Реализует retry‑логику.

---

## Retry‑политика (MVP)

- Retry применяется:
  - **только для GET**;
  - только для:
    - network‑ошибок,
    - `502 / 503 / 504`.
- Retry **не применяется** для `401`.
- Максимум — **3 попытки**.
- `AbortSignal` всегда учитывается.
- Retry централизован и недоступен для управления из Page.

---

## Стратегия страниц (Page)

### Ключевое правило
> **У страницы есть одна функция `load()` — единственный источник истины загрузки.**

### Поведение `load()`
- abort предыдущего запроса;
- создание нового `AbortController`;
- перевод `uiState` в `loading`;
- вызов `loadPageData`.

### Использование
- `useEffect` → `load()`;
- `PageShell.onRetry` → `load()`.

Ручная смена `uiState` без запроса запрещена.

---

## PageShell и Retry

- `PageShell`:
  - не знает, как выполняется загрузка;
  - отображает состояния (`loading / empty / error / default`);
  - вызывает `onRetry`.
- Auto‑retry:
  - снижает количество transient‑ошибок;
  - **не заменяет** кнопку Retry.

---

## Backend‑контракты (ожидания)

### Коллекции
- всегда возвращается `[]`, не `null`;
- `200 OK` — единственный успешный код.

### Ошибки
- `400 / 404` → `ProblemDetails`;
- `409` → допустим plain text (MVP);
- файлы (`text/csv` и др.) — отдельные download‑эндпоинты.

---

## Инварианты (изменение = новый ADR)

- Нет refresh‑токенов.
- `401` — глобальный logout, не ошибка экрана.
- HTTP и retry не живут в Page.
- Одна функция загрузки на страницу.
- Retry только централизованный.

---

## Out of Scope
- Refresh‑токены и сложные auth‑flow.
- Circuit breaker, exponential backoff.
- Полная спецификация API эндпоинтов.
- Backend‑реализация контроллеров.
