# ADR 0023: Frontend tooling & code style (MVP)

## Почему

В рамках MVP необходимо зафиксировать **базовые договорённости по инструментам и стилю кода фронтенда**, чтобы:

* избежать расхождений в импортах и форматировании;
* упростить навигацию и рефакторинг;
* обеспечить единый и предсказуемый стиль кода в учебном и командном проекте.

Данный ADR фиксирует **минимальный и достаточный набор решений**, не выходя за рамки MVP.

## Контекст

Репозиторий использует:

* React + Vite + TypeScript;
* ESLint для контроля качества кода;
* VS Code как основной редактор (де-факто для команды).

Без формальной фиксации эти решения быстро превращаются в “неявные договорённости”.

## Решение

### Path alias (`@/`)

В проекте используется alias:

```
@/ → src/
```

**Назначение:**

* устранение глубоких относительных импортов (`../../..`);
* повышение читаемости кода;
* упрощение перемещения файлов и рефакторинга.

**Где настраивается:**

* TypeScript (`tsconfig.app.json`);
* Vite (`resolve.alias`).

Решение принято как стандартное и достаточное для MVP.

---

### VS Code project settings

В репозитории присутствует файл:

```
.vscode/settings.json
```

**Назначение:**

* единый стиль форматирования;
* автоисправление простых ESLint-ошибок;
* автоматическое обновление импортов при перемещении файлов.

**Ограничения:**

* настройки носят рекомендательный характер;
* применяются только в VS Code;
* не влияют на сборку и CI;
* игнорируются другими IDE.

---

### Semicolons (`;`)

В проекте используются **обязательные точки с запятой** во всех файлах JavaScript / TypeScript.

**Причины:**

* устранение edge-case’ов Automatic Semicolon Insertion (ASI);
* предсказуемый и единый стиль кода;
* снижение когнитивной нагрузки в учебном проекте.

**Контроль:**

* ESLint: `semi: ["error", "always"]`;
* отсутствие `;` считается ошибкой;
* JSX не затрагивается.

## Следствия

* Все фронтенд-файлы следуют единым правилам импортов и форматирования.
* Стиль кода проверяется автоматически ESLint’ом.
* Инструментальные договорённости считаются зафиксированными для MVP и не обсуждаются повторно без нового ADR.

## Out of Scope

* Выбор альтернативных редакторов и IDE.
* Расширенные code-style правила (Prettier, кастомные плагины и т.п.).
* Non-MVP усложнение tooling и pipeline.
