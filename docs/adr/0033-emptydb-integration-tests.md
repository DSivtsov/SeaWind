# ADR 0033 — EmptyDb для интеграционных API‑тестов

## Зачем / Контекст

1. Интеграционные API‑тесты должны выполняться на полностью чистой базе данных без неявных зависимостей от сидирования.
2. Для тестов необходимо изолированное окружение, в котором каждый тест работает со своей БД и не влияет на другие тесты.
3. Интеграционные тесты с авторизацией должны выполняться без реального auth‑пайплайна.

---

## Решения

### 1. Режим EmptyDb для интеграционных тестов

Вводится режим `EmptyDb`, используемый при запуске тестового Web-сервера
для интеграционных API-тестов.

Режим `EmptyDb` применяется в контексте ASP.NET test-hosting
(`WebApplicationFactory`) и позволяет запускать приложение
в изолированной конфигурации, предназначенной для тестов.

В режиме `EmptyDb` при запуске сервера:
- выполняются только EF-миграции;
- сидирование данных отключено.
- Режим активируется через тестовые настройки окружения.
- Поведение базы данных в тестах становится предсказуемым и контролируемым.

Это позволяет писать интеграционные тесты, которые:
- выполняются на реальной СУБД (PostgreSQL), а не на in-memory заменах;
- проверяют реальные миграции, индексы и ограничения схемы;
- выявляют проблемы, не проявляющиеся в unit-тестах (сортировки, nullability, unique-constraints, транзакции);
- проверяют поведение API в условиях, максимально близких к реальной среде выполнения.

---

### 2. Использование изоляция базы данных на уровень теста

- Каждый интеграционный тест работает с отдельной чистой БД.
- Для каждого теста создаётся отдельный `MainDbContext` scope.
- Используется контейнер PostgreSQL, поднимаемый на время тестов.
- База данных не переиспользуется между тестами.

Это исключает влияние порядка выполнения тестов и скрытых побочных эффектов.

---

### 3. Тестовая авторизация для API‑тестов

Для интеграционных API‑тестов вводится тестовый auth‑обработчик.

- Используется `TestAuthHandler`:
  - всегда аутентифицирует запрос;
  - возвращает фиксированный набор claims (включая роль).
- Тестовая схема авторизации применяется только в тестовой среде.
- Реальный auth‑пайплайн в тестах не используется.

Это позволяет писать интеграционные тесты для защищённых API без зависимости от auth‑инфраструктуры.

### 4. Кратко: пример использования (инструкция)
```cs
// 1. Подключение контейнерной фикстуры
// Класс тестов помечается коллекцией, чтобы использовать общий контейнер БД
[Collection("ContainerDb collection")]
public class CoursesControllerTests
{
    private readonly HttpClient _client;
    private readonly WebApplicationFactory<Program> _factory;
    private readonly ContainerDbFixture _fixture;

    // 2. Получение параметров через конструктор теста
    // HttpClient используется для вызова API
    // WebApplicationFactory — для доступа к DI и создания scope
    public CoursesControllerTests(ContainerDbFixture fixture)
    {
        _fixture = fixture;
        _factory = fixture.Factory;
        _client = fixture.Client;
    }

    [Fact]
    public async Task Example_Test()
    {
        // 3. Приведение БД в чистое состояние (EmptyDb)
        // Выполняются только миграции, без сидирования
        await _fixture.ResetMainDbAsync();

        // 4. Явная подготовка данных (Arrange)
        // Данные добавляются напрямую через MainDbContext
        using (var scope = _factory.Services.CreateScope())
        {
            var db = scope.ServiceProvider.GetRequiredService<MainDbContext>();

            // db.<Entity>.Add / AddRange(...)
            // await db.SaveChangesAsync();
        }

        // 5. Вызов API (Act)
        var response = await _client.GetAsync("/api/courses");

        // 6. Проверка результата (Assert)
        // response.StatusCode
        // response.Content
        // десериализация и проверки бизнес-ожиданий
    }
}

```
