# ADR 0019: Integration Tests With Testcontainers (API → PostgreSQL)

**Дата:** 2025-11-29

## 1. Причина решения

В процессе длительной разработки проекта необходим механизм фиксации и контроля уже созданной функциональности.
Для BackEnd это достигается с помощью автоматизированных тестов. В рассматриваемом проекте целесообразно использование двух основных типов тестов: **Unit-тестов** и **Integration-тестов**.

---

### 1.1. Сравнение UnitTest и IntegrationTest

| Критерий                 | Unit Tests                                                    | Integration Tests                                             |
| ------------------------ | ------------------------------------------------------------- | ------------------------------------------------------------- |
| **Фокусировка проблемы** | Позволяют точно локализовать ошибку в конкретном методе       | Ошибка может проявляться на стыках слоёв; локализация сложнее |
| **Стоимость разработки** | Высокая, особенно при попытке покрыть весь API/бизнес-флоу    | Ниже — один тест покрывает сразу несколько слоёв              |
| **Где оправданы**        | Сложные алгоритмы, парсеры, расчёты, валидации                | CRUD-операции, API-эндпоинты, сквозные сценарии               |
| **Когда полезны**        | При рефакторинге, когда важно фиксировать изменение поведения | Для проверки работы приложения в целом                        |

---

### 1.2. Вывод

Оба подхода имеют свои преимущества, однако с учётом:

* учебного характера проекта,
* ограниченности ресурсов,
* отсутствия планов по активному рефакторингу,
* практических рекомендаций по организации тестирования  (см. [Creation_Testing_Notes](https://github.com/DSivtsov/SeaWind/wiki/Creation_Testing_Notes)),

масштабное покрытие Unit-тестами будет неоправданно затратным.

Интеграционные тесты дают более высокую отдачу: один тест автоматически охватывает весь путь запроса и позволяет выявлять ошибки на стыках слоёв.

Путь выполнения:
**HTTP → Middleware → Контроллер → Application Layer → EF Core → PostgreSQL**

Поэтому в рамках проекта интеграционные тесты выбираются как **основной тип тестов для API**.

## 2. Integration Test: варианты использования БД

Для корректной работы интеграционных тестов требуется взаимодействие с реальной БД или с максимально близким эквивалентом.
В рассматриваемом проекте анализировались три варианта.

---

### 2.1. Сравнение доступных вариантов

| Вариант БД                         | Плюсы                                                                                                               | Минусы                                                                                                                                  |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| **EF Core InMemory Provider**      | Очень высокая скорость; простая конфигурация; не требует Postgres                                                   | Не соответствует поведению PostgreSQL: отсутствуют SQL-механизмы, транзакции, индексы, типы; невозможно проверить поведение реальной БД |
| **Отдельная тестовая Postgres-БД** | Реальный Postgres; поддержка миграций; максимальная близость к PROD                                                 | Требуется очистка между тестами; риск зависимостей между тестами; более сложная настройка CI                                            |
| **Postgres через Testcontainers**  | Реальный Postgres; чистая БД при каждом запуске; полная изоляция; легко интегрируется в CI; повторяемость окружения | Более долгий старт контейнера; требование Docker; конфигурация сложнее, чем у InMemory                                                  |

---

### Примечания по вариантам

#### **InMemory Provider**

Использование InMemory в роли тестовой БД оказалось непрактичным для интеграционных сценариев.
Основные проблемы:

* отсутствует поддержка SQL-поведения (каскады, ограничения, транзакции);
* несоответствие обработке типов PostgreSQL;
* невозможность корректно тестировать сидирование (логика Postgres не повторяется);
* необходимость писать параллельный код вставки и заполнения данных.

В результате InMemory может применяться только для изолированных Unit-тестов, но **не подходит для интеграционного уровня**.

---

#### **Отдельная тестовая Postgres-БД**

Этот вариант функционально близок к Testcontainers, и в большинстве случаев различия минимальны.
Преимущества:

* привычная и простая интеграция с CI (без контейнеризации), если уже существует настроенное окружение;
* возможность выполнения миграций в «постоянную» тестовую БД.

Недостатки:

* требуется схема очистки и сброса состояния;
* риск пересечения данных между тестами или сборками;
* требуется поддерживать отдельную БД в CI, что усложняет конфигурацию.

В целом переключение между этим вариантом и Testcontainers несложно, но Testcontainers обеспечивает более предсказуемый и изолированный цикл.

---

### 2.2. Выбор

Исходя из требований проекта — изоляция среды, гарантированно чистая БД, возможность повторяемого запуска локально и в CI — выбран вариант:

## **PostgreSQL в Testcontainers**

### **Основные причины выбора**

* обеспечивает максимальную изоляцию окружения тестов (каждый запуск использует независимую среду);
* гарантирует высокую повторяемость и детерминированность результатов;
* позволяет автоматически поднимать PostgreSQL без дополнительной ручной конфигурации или подготовки окружения;
* обеспечивает естественную очистку состояния между тестами за счёт изоляции контейнера;
* упрощает интеграцию в CI/CD, так как окружение формируется автоматически и не требует внешней инфраструктуры.

Этот вариант создаёт наиболее устойчивую и прогнозируемую среду для интеграционных тестов и снижает операционные затраты на поддержку тестовой инфраструктуры.

## 3. Как закрываются минусы Testcontainers

### 3.1 Производительность
Используются:
- **xUnit CollectionFixture**
  `ContainerDbCollection : ICollectionFixture<ContainerDbFixture>`
  Контейнер создаётся **один раз на коллекцию**, а не на каждый тест.

### 3.2 Соответствие основной БД
Используются SQL-скрипты в папке `TestcontainerInitDb`:

- создание схемы
- создание ролей
- выдача прав
- установка search_path
- подготовка структуры БД, идентичной PROD

Контейнер запускается с монтированием каталога инициализации:

`/docker-entrypoint-initdb.d/000_init_db.sql`

### 3.3 Отключение ненужных сервисов API
Через `ContainerDbWebApplicationFactory` устанавливаются переменные окружения:

```
WC_USE_TEST_SETTINGS=true
ConnectionStrings__Default=<контейнерная строка подключения>
```

В режиме тестов приложение:
- отключает лишние сервисы
- не поднимает тяжёлые background-jobs
- не регистрирует внешние интеграции
- использует минимальную конфигурацию

## 4. Архитектура решения

### 4.1 ContainerDbFixture
Основные функции:
- создаёт Postgres-контейнер через Testcontainers
- подключает SQL-скрипты для инициализации схемы
- ждёт готовности БД через WaitStrategy
- создаёт `ContainerDbWebApplicationFactory`
- отдаёт `HttpClient` интеграционным тестам
- сохраняет лог запуска БД в рабочей директории проекта тестов — файл `tests\Api.UnitTests\bin\Debug\net8.0\postgres_log.txt` (если запускается в режиме Debug)
- корректно завершает контейнер

### 4.2 ContainerDbWebApplicationFactory
Переопределяет `CreateHost`:

- подменяет строку подключения на контейнерную
- активирует тестовый режим API
- создаёт `HttpClient`, полностью готовый к интеграционным тестам

### 4.3 ContainerDbCollection
Объявление коллекции:

```
[CollectionDefinition("ContainerDb collection")]
public class ContainerDbCollection : ICollectionFixture<ContainerDbFixture> {}
```

Гарантирует:
- создание контейнера один раз
- расшаривание фикстуры между всеми тестами коллекции

---

## 5. Пример использования

Файл: `CoursesController_GetAll_Tests_Testcontainers.cs`

Пример:

1. Подключаемся к коллекции:

```
[Collection("ContainerDb collection")]
```

2. Берём `HttpClient` из фикстуры:

```
_client = testcontainerFixture.Client;
```

3. Запускаем настоящий API-запрос:

```
var response = await _client.GetAsync("/api/courses");
```

4. Проверяем результат:

- статус 200
- десериализуем JSON
- проверяем корректность данных

## 6. Альтернативный тестовый режим (без Testcontainers)
Помимо основного механизма интеграционного тестирования на базе Testcontainers, в проекте предусмотрен упрощённый fallback-вариант:

* **TestDbWebApplicationFactory**
* **TestDbFixture**
* **TestDbCollection**

Этот режим не использует контейнеризированную временную БД Testcontainers.
Он запускает API с подключением к отдельной тестовой PostgreSQL-БД.

❗ Все тесты, использующие тестовую PostgreSQL-БД, должны находиться в **namespace** `Api.UnitTests.IntegrationTestDB`,
так как данный режим не совместим с **CI** (будет приводить к ошибкам при запуске).
Такие тесты автоматически исключаются из **CI** при помощи фильтрации по этому **namespace**.

### Цели и назначение

* возможность запуска интеграционных тестов **без Docker**;
* минимальное время старта тестов (удобно при локальной разработке);
* учебный режим и отладка тестов без необходимости поднимать инфраструктуру Testcontainers.

### Требования и подготовка

Использование данного режима предполагает наличие **отдельной тестовой БД PostgreSQL**:

1. Все необходимые конфигурационные файлы присутствуют в `docker/`.
2. Для запуска тестовой БД достаточно создать тестовый контейнер:

```
cd docker
docker compose --env-file .env.test -f docker-compose.test.yml up
```

3. При первом выполнении теста `CoursesController.GetAll()`
   будут автоматически применены миграции и выполнено сидирование таблиц.
   Используются те же демо-данные, что и для основной БД.

4. К тестовой БД можно подключаться через DBeaver
   (параметры подключения указаны в `.env.test`).

5. Тестовая БД полностью независима от основной,
   обе могут работать параллельно без конфликтов.

### Ограничения режима

* не проверяет поведение EF Core + PostgreSQL в изолированной среде;
* нет автоматической очистки состояния между тестами;
* не обеспечивает детерминированность, сравнимую с Testcontainers.
* не поддерживается CI (будут постоянно ошибки)

### Статус

Режим рассматривается как **вспомогательная инфраструктура**,
которая дополняет, но не заменяет основной подход на Testcontainers.

## 7. Out of Scope
- тестирование фронтенда
- нагрузочные тесты
- тесты с участием внешних API
- long-running background tests
