# ADR 0011: Хранение Data Protection Keys в контейнерах

**Дата:** 2025-10-10

## Решение
Ключи ASP.NET Data Protection сохраняются в постоянное хранилище (bind mount), а не во временном каталоге контейнера.
* Внутри контейнера ASP.NET настроено хранилище `/keys`, которое монтируется на локальную директорию `\docker\dpkeys` проекта.
* В `Program.cs` добавлен метод `AddStorageForContainers()` (см. коммит [Fix : Устранение warnings при запуске и оптимизация сборки контейнера](https://github.com/DSivtsov/SeaWind/pull/63)), который подключает это хранилище к приложению.

## Почему
Если ничего не настраивать:
* На Windows-машине ключи пишутся в `%LOCALAPPDATA%\ASP.NET\DataProtection-Keys`.
* В **контейнере Linux** (как у нас) — в `/root/.aspnet/DataProtection-Keys`.

ASP.NET Data Protection автоматически создаёт XML-файлы с ключами в выбранной директории.
Однако в контейнере этот каталог временный: при `docker compose down` или пересборке образа он удаляется.
После этого старые ключи теряются, и прежние куки невозможно расшифровать → пользователи будут разлогиниваться при перезапуске **API-сервиса**.

Это нарушает требование доступности сервисов и вызывает предупреждение:
> "Storing keys in '/root/.aspnet/DataProtection-Keys' that may not be persisted outside of the container"

## Следствие
✅ Пользователи остаются авторизованными при перезапусках контейнера. 💪
✅ Предупреждение о временном хранилище ключей исчезает.


## Примечания
Рекомендации на будущее: для окружений **TST/PRD** использовать **общий key-ring** (например, NFS или Redis), чтобы все инстансы приложения могли расшифровывать одни и те же ключи.
Подробнее см. *Architecture_Overview_Current.md* → раздел **Data Protection**.
