# ADR 0032 — PageShell, AppShell, demoCoursesApi (Frontend)

## Зачем / Контекст

1. На каждой странице необходимо единым образом обрабатывать возможные состояния (`loading / empty / error / ready`) за счёт использования общего врапера (компонента).
2. Большинство страниц имеют одну и ту же базовую архитектуру на основе `AppShell` (Header / Main / Footer) с повторяющимися параметрами.
3. При разработке страниц необходимо иметь возможность их тестирования и проверки без готового бекенда.

---

## Решения

### 1. Единая обработка состояний страницы (PageShell)

Для унификации обработки состояний страниц используется общий компонент `PageShell`.

- `PageShell` применяется **внутри страниц**, а не в layout’ах.
- Страница формирует собственное состояние (`loading / empty / error / ready`) и передаёт его в `PageShell`.

Фиксированный набор состояний:
- `loading` — данные страницы загружаются;
- `empty` — данных нет, но состояние валидно;
- `error` — ошибка загрузки данных;
- `ready` — нормальный рендер контента.

PageShell:
- не делает запросов;
- не знает источник данных;
- не знает про курсы, табы, роли и маршруты.

Специфичный UI страницы передаётся через параметры:
- `loadingView?: React.ReactNode`
- `emptyView?: React.ReactNode`

Вся визуальная специфика передаётся извне через параметры страницы.
`PageShell` не управляет layout-структурой страницы и навигацией.
Размещение header, navbar, footer и responsive-поведение относятся к ответственности layout-уровня (`AppFrame`).

---

### 2. Базовая архитектура страниц на основе AppShell

Mantine `AppShell` используется как **общий инфраструктурный каркас приложения**.

Для устранения дублирования вводится единый `AppFrame` — обёртка над `AppShell`, используемая как единая точка подключения layout-инфраструктуры, а также инкапсулирует конфигурацию каркаса и responsive-логику.

---

### 3. Использование AppFrame для разработки страниц

`AppFrame` используется как единый layout-хост для всех экранов приложения.

#### Назначение

`AppFrame` отвечает **только за каркас страницы** и не содержит логики конкретных экранов.

В зону ответственности `AppFrame` входят:

* размещение `header`, `navbar`, `footer`
* интеграция с Mantine `AppShell`
* адаптация под wide / narrow экраны
* поддержка `Navbar` (wide) и `Drawer` (narrow)

#### Ограничения

`AppFrame` **не должен**:

* хранить состояние навигации
* определять активный пункт меню
* содержать логику экранов или бизнес-правила
* синхронизироваться с URL

#### Навигация

Навигация между экранами внутри layout осуществляется **исключительно через routing**:

* используется `react-router-dom/NavLink`
* URL является **единственным источником истины**
* UI-компоненты (`Mantine NavLink`, `Tabs`) применяются только как визуальное представление

Активное состояние пункта:

* определяется роутером
* визуально выделяется
* **не переводится в disabled**

#### Использование в layout-ах

`AdminLayout`, `CourseLayout` и другие layout-компоненты:

* используют `AppFrame` как общий контейнер
* передают собственные `header` и набор навигационных ссылок
* не дублируют layout-логику
* Навигация между экранами layout-уровня осуществляется через routing (NavLink).
UI-компоненты навигации (Tabs, NavLink Mantine) не управляют переходами и не хранят состояние навигации.

#### Решение по `AppShell.Main`

- `AppShell.Main` принимает **`children`**;
- `Main` **не передаётся пропсом**;
- не используются render-props или callback-схемы.

Решение принято для упрощения архитектуры и повышения читаемости дерева компонентов.

---

### 4. Разделение ответственности (итоговая схема)

```
Route / Layout
 └─ AppFrame (AppShell: Header / Main / Footer / Navbar)
     └─ PageContainer (данные и state)
         └─ PageShell (loading / empty / error / ready)
             └─ Content
```

Роли уровней:

- **AppFrame** — структура приложения;
- **PageContainer** — загрузка данных и управление состоянием;
- **PageShell** — визуальное состояние страницы;
- **Content** — конкретный UI экрана.

---

### 5. Использование заглушек бекенда для разработки UI (demoCoursesApi)

Для разработки и проверки UI без готового бекенда используется слой заглушек API.

- Используется файл `demoCoursesApi.ts` (и аналогичные при необходимости).
- Заглушки:
  - повторяют контракт реального API;
  - позволяют имитировать задержки, empty- и error-сценарии;
  - используются страницами так же, как реальный API.
- При появлении настоящего бекенда заменяется реализация API, а не код страниц.
