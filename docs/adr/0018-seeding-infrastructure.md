# ADR 0018: Организация загрузки демо данных (Seeding)
**Дата:** 2025-11-13

## Почему
Для WorkshopCode нужно было получить **повторяемую и управляемую загрузку демо-данных** в разные `DbContext` (Main, Time, Identity) для DEV среды, без ручного SQL и одноразовых скриптов.  
Требования:
*   сидирование должно выполняться только в Dev-окружении,
*   данные должны **синхронизироваться с моделью EF Core** (Code First + миграции),
*   демо-данные хранятся в виде **текстовых JSON-файлов**,  а в качестве средства подготовки этих файлов используется **Google Sheets (лист `DataModel`) + скрипт** для экспорта в JSON.
*   в демо-данных значения первичных и внешних ключей указываются в **человеко-читаемой форме**, например: `!cars.1`, `!tester.4` — такие маркеры легко вводить в таблицу, и при загрузке они автоматически преобразуются в реальные PK/FK.
*   сидирование должно поддерживать разные режимы загрузки данных, включая:
    -  **идемпотентный режим** (upsert по ключу),
    -  режим **полной замены данных** (*fresh install*) при необходимости.
*   включаться/выключаться и настраиваться **через `appsettings.*`**, при этом **никакие параметры не должны быть захардкожены в коде**,
*   при этом вся логика должна быть **централизована** в backend-слое `Infrastructure.Postgres`, а запуск прозрачный для `Api`.
*   для загрузки данных используются отдельные DTO для сидирования в `Infrastructure.Postgres` (не использовать DTO из `Application`)
*   используемые модели таблиц (сущностей) описываются через `public class` (с обычными `get; set;`), чтобы EF Core корректно отслеживал состояние объектов

## Решение
### 0. Общая идеология
Модель данных WorkshopCode, как и большинство прикладных моделей, представляет собой
**ориентированный ацикличный граф (DAG)** зависимостей между сущностями.

Стратегия загрузки данных в WorkshopCode:
* сидирование должно опираться на **DAG-структуру модели данных**,
* порядок выполнения сидеров определяется через **топологическую сортировку** графа зависимостей,
* загрузка/удаление данных выполняется строго в соответствии с этим порядком
  (от корневых сущностей → к зависимым; при wipe — в обратном направлении).

Более подробно про **DAG** см **[Общие подходы к организации сидирования](https://github.com/DSivtsov/SeaWind/wiki/SeedingOrganization)**,
а также рекомендованный порядок для текущей [ER-модели WorkshopCode](https://github.com/DSivtsov/SeaWind/blob/develop/docs/WorkshopCode_ER_MVP.md)

### 1. Архитектура решения
#### Основные модули
1. Главный раннер (`MainRunner`)
    * Запускает все зарегистрированные `IDbContextRunner`.
    * Валидирует секцию `Seed:CoreOption` из **appsettings**.
    * Загружает и анализирует выбранный **пресет сидирования** (`Seed:Preset` в **appsettings**), определяя общий набор правил и поведения для всех DbContext.

2. `RunnerContextDB<TContext>` — отдельный раннер для каждого сидируемого DbContext
    * На основании `Seed:{DbContext}:*` из **appsettings** и выбранного **пресета** формирует итоговые опции сидирования (`Options`).
    * Для каждого DbContext выполняет:
        * анализ и валидацию опций (`Options`);
        * запуск раннера подготовки файлов (`RunnerSeedDataFiles`) — парсинг seed-файлов, проверка PK/FK, построение DAG;
        * проверку готовности DbContext или применение миграций (`AutoMigrate = true`) через `Checker`;
        * анализ изменения опций сидирования, которые могут сделать ранее загруженные данные несовместимыми с новым запуском (в этом случае требуется полная очистка — `ExistenData = Fresh`);
        * удаление данных (“полная очистка”) через `Cleaner<TContext>`; в зависимости от выбранных опций сидирования может быть принудительной или рекомендованной;
        * запуск сидера (`Seeder<TContext>.RunSeedingAsync(...)`), выполняющего загрузку данных таблица-за-таблицей.

3. Сидер (наследуется от `BaseSeeder<TContext, TEntity, TDto>`) — отдельный сидер для каждой сущности
    * Реализует 4 обязательные операции (abstract methods from `BaseSeeder<...>`)::
        * поиск сущности по PK,
        * добавление новой сущности,
        * обновление всех полей существующей сущности,
        * удаление записей.
    * Определяет порядок загрузки/удаления данных (**ранг таблицы**, `SeedOrder`) согласно графу зависимостей (DAG).
    * Работает с DTO и JSON-файлами, подготовленными в процессе `RunnerSeedDataFiles`.

---

#### Данные для сидирования
* Исходные JSON-файлы (создаваемые разработчиками) должны:
  * соответствовать **правилам задания PK/FK** (формат `!entity.number`);
  * иметь имена по шаблону `Demo{Entity}.seed.json`
    (например: `DemoTester.seed.json`);
  * лежать в корректных директориях `*DbContext*/SeedData`.

* Перед выполнением сидирования будет произведена их подготовка:
  * исходные файлы копируются в рабочую директорию `AppContext.BaseDirectory`
    (в Debug для **TimeDbContext**: `Api\bin\Debug\net8.0\Time\SeedData\`);
  * выполняется их **парсинг**, **проверка PK/FK**, построение зависимостей.

* Потом на их основе создаются *выходные файлы* данных:
  * генерируются рабочие файлы `Demo{Entity}.json` (например `DemoTester.json`);
  * всем PK/FK назначаются **UUID** (способ зависит от выбранных опций сидирования);
  * файлы сохраняются в рабочей директории и используются при последующих запусках.

ℹ **Важно:**
Все пути в настройках (*для исходных файлов*) указываются относительно проекта **Infrastructure.Postgres** (где они хранятся).  
При запуске приложения **все эти файлы копируются вместе с DLL Infrastructure.Postgres в рабочую директорию проекта Api**  
(например: `Api\bin\Debug\net8.0\Time\SeedData\`).

Именно в этой рабочей директории создаются *выходные файлы* (`Demo{Entity}.json`),  
и именно они используются для фактической загрузки данных в таблицы.

---

#### Пресеты сидирования
Управление сидированием выполняется через набор **опций сидирования**, однако для удобства рекомендуется использовать **пресеты** — заранее определённые сочетания ключевых параметров (`Seed:Preset` в *appsettings*).

- Если указан пресет `Preset = SeedCustom` (или параметр отсутствует), действует *классический режим*: все параметры берутся из отдельных опций.
- Если выбран один из пресетов `Preset = SuperFast | Fast | Real`, он имеет приоритет и полностью переопределяет соответствующие опции сидирования для **всех** DbContext.

| Preset      | UUID       | ExistingData | Mode            | AutoMigrate | Назначение |
|-------------|------------|--------------|-----------------|-------------|------------|
| SeedOFF     | —          | —            | —               | —           | Полное отключение сидирования |
| SeedCustom  | —          | —            | —               | —           | Ручная настройка, пресеты не применяются |
| SuperFast   | Stable     | NotDelete    | InsertOnly      | true        | Максимально быстрый запуск, без обновлений |
| Fast        | Stable     | NotDelete    | InsertOrUpdate  | true        | Быстрый запуск с обновлениями |
| Real        | Real       | Fresh        | InsertOnly      | true        | Полная пересборка данных из seed-файлов |

---

#### Опции сидирования
Параметры управления сидированием находятся в секции **`Seed`** файла `appsettings.Development.json`.  
Некоторые опции взаимосвязаны — при настройке это важно учитывать.

Опции делятся на два уровня:

1. Глобальные параметры (`Seed:CoreOption`)

    Используются для построения имён и шаблонов файлов:
    * **`FileNameDataTemplate`** — шаблон имени рабочих файлов демо-данных
    *(например: `"Demo{Entity}.json"` → `DemoTester.json`)*.
    * **`FileNameSeedTemplate`** — шаблон исходных seed-файлов
    *(например: `"Demo{Entity}.seed.json"` → `DemoTester.seed.json`)*.
    * **`SuffixSeederClassName`** — суффикс имени класса сидера
    *(например: `"Seeder"` → `Tester` + `Seeder` = `TesterSeeder`)*.

2. Опции для каждого DbContext

    Каждый контекст имеет собственный раздел `"Seed:{DbContextName}"` (могут расширяться/уменьшаться при изменение используемых контекстов):
    * **`Enabled`** — включение/выключение сидирования для этого DbContext.
    * **`PathBase`** — путь к seed-файлам, скопированным в рабочий каталог (должен быть согласован с настройками `CopyToOutputDirectory` в `Infrastructure.Postgres.csproj`).
    * **`Mode`** — режим вставки:
        * `InsertOnly` — только вставляет; при наличии записи с тем же PK данные не изменяются.
        * `InsertOrUpdate` — вставляет и обновляет существующие, при наличии записи с тем же PK ее значения будут полностью обновлены.  
            (❗ **корректно работает только** при `UUID = Stable`; при `UUID = Real` PK будут разными на каждом запуске.)
    * **`UUID`** — стратегия генерации GUID:
        * **`Real`** — генерация GUID по стандартным правилам (`Guid.NewGuid()`), каждый запуск создаёт новые значения.
        * **`Stable`** — детерминированные GUID (UUIDv5): одно и то же ключевое значение (`!Cars.1`) всегда получает **один и тот же** GUID.            
    * **`ExistenData`** — режим действий по отношению к уже существующим данным в таблицах (как созданным вручную, так и оставшимся после предыдущих импортов):
        * **`Fresh`** — удалить **все** записи перед загрузкой.
        * **`NotDel`** — не удалять существующие записи.
            *(❗ Корректно работает только при `UUID = Stable`; при `UUID = Real` PK будут разными на каждом запуске, что приведёт к накоплению дубликатов — старые записи сохраняются, а новые получают новые PK.)*
    * **`AutoMigrate`** — автоматически выполнять миграции при наличии *pending* миграций.  
        *(ℹ Если `AutoMigrate = false`, сидирование будет остановлено до тех пор, пока отложенные миграции не будут применены вручную через `dotnet ef database update`.)*

### Подключение инфрастуктуры сидирования

#### Регистрация в DI
Все компоненты сидирования регистрируются в `Infrastructure.Postgres\DbSeedersDI.cs`.

**Не требуют дополнительной настройки:**
* критично важные параметры, определяющие форматы имён файлов (`SeedCoreParameters`);
* вспомогательные сервисы (`Cleaner<>`, `PathFile`, `ISeedCoreOptions`, `SeedPresetAnalyzer`);
* базовые компоненты инфраструктуры сидирования:
  * интерфейс запуска сидирования (`IMainRunnerSeeding → MainRunner`);
  * generic-оркестратор сидеров (`Seeder<>`);
  * generic-оркестратор очистки (`Cleaner<>`).

**Требуют уточнения только при добавлении/изменении количества сидируемых DbContext:**
* основные раннеры (`IMainRunnerSeeding`, `IDbContextRunner`).
```c#
services.AddScoped<IDbContextRunner, RunnerContextDB<MainDbContext>>();
services.AddScoped<IDbContextRunner, RunnerContextDB<TimeDbContext>>();
```

**Необходимо задавать для каждой сидируемой таблицы:**
* соответствующие сидеры (`ISeeder<TContext>`).
```c#
services.AddScoped<ISeeder<TimeDbContext>, TesterSeeder>();         # для сущности Tester
services.AddScoped<ISeeder<MainDbContext>, CourseSeeder>();         # для сущности Course
```
---

#### Запуск процесса сидирования

1. **Сервисы сидирования регистрируются в DI** через вызов:
   `builder.Services.DbSeedersDI(cfg);`

2. **Выполнение сидирования происходит в Program.cs**, *только в окружении Development*:

   ```csharp
   if (app.Environment.IsDevelopment())
   {
       await using var scope = app.Services.CreateAsyncScope();
       var mainRunner = scope.ServiceProvider.GetRequiredService<IMainRunnerSeeding>();
       await mainRunner.Run(app.Lifetime.ApplicationStopping);
   }
   ```

3. При запуске хоста:
   * создаётся **асинхронный scope** (`CreateAsyncScope`);
   * из него извлекается `IMainRunnerSeeding` — главный раннер сидирования;
   * запускается сидирование методом `Run(...)`;
   * в качестве `CancellationToken` передаётся `app.Lifetime.ApplicationStopping`,
     что обеспечивает корректную остановку процесса при завершении приложения.

4. Сидирование выполняется **после `Build()`**, но **до начала обработки входящих HTTP-запросов**,
   то есть **перед запуском API** в режиме Development.

5. Для всех фаз сидирования реализована **обработка исключений** и подробное **логирование** (`ILogger`):
   * старт и завершение сидирования каждого DbContext;
   * выполнение всех этапов подготовки и загрузки данных;
   * обнаружение и пропуск некорректных записей в seed-файлах:
     * FK, ссылающиеся на отсутствующие PK;
     * повторяющиеся PK;
   * ошибки десериализации JSON (несовместимые типы данных);
   * ошибки работы с БД (миграции, обновления, сохранение данных).

   При необходимости уровень детализации логирования настраивается через `appsettings.*` как для обычного логирующего сервиса.

### Добавление новой сущности в систему сидирования
Чтобы добавить демо-данные для новой сущности,  
(далее для примера используется сущность `Course` из `MainDbContext`).

1. **Описание модели в Application + EF Core**
* В проекте `Application` создать модель домена:
  - для сущности `Course` — `Application\Models\Course.cs`;
  - модель должна быть реализована как **`public class` с обычными `get; set;`**,
    чтобы EF Core корректно отслеживал состояние объектов (Tracking),
    выполнял обновления (`Update`) и использовал Change Tracker;
  - пример корректной модели:
```csharp
public class Course
{
    public Guid Id { get; set; }
    public string Title { get; set; } = null!;
    public string? Code { get; set; }
    public string? Description { get; set; }
    public DateTime? CreatedAt { get; set; }
    public DateTime? UpdatedAt { get; set; }

    // Обязательный пустой конструктор для EF
    public Course() { }

    // Удобный конструктор для ручного создания сущности
    public Course(Guid id, string title, string? code, string? description, DateTime? createdAt, DateTime? updatedAt)
    {
        Id = id;
        Title = title;
        Code = code;
        Description = description;
        CreatedAt = createdAt;
        UpdatedAt = updatedAt;
    }
}
```
  * В проекте `Infrastructure.Postgres` в описание нужного `DbContext`
  добавить сущность (`DbSet<...>`) и её конфигурацию — либо прямо в `OnModelCreating(...)`,
  либо вынести в отдельный класс-конфигурацию (`IEntityTypeConfiguration<T>`) (для `Course` — `Infrastructure.Postgres\Main\MainDbContext.cs`)
   
   * Скомпилировать проект и создать миграцию (EF Core Code First):
   
```bash
cd src/backend/Infrastructure.Postgres

# пример для MainDbContext, имя миграции можно выбрать любое понятное
dotnet ef migrations add InitCourse -c MainDbContext -p . -o Main/Migrations -v
```
❗ **ВАЖНО:** перед запуском сидирования необходимо выполнить миграцию модели данных вручную или включить опцию сидирования `AutoMigrate = true`.
```bash
cd src/backend/Infrastructure.Postgres

# выполнение ручной миграции (пример для MainDbContext)
dotnet ef database update -c MainDbContext -p . -v
```

2. **DTO для сидирования**
  * Для каждой новой таблицы, которая участвует в сидировании через JSON,
  создаётся отдельный DTO в проекте `Infrastructure.Postgres` (не использовать DTO из `Application`)
  * Простое правило размещения:
    * сущности из `MainDbContext` — DTO в `Infrastructure.Postgres\Main\SeederDto\<Entity>SeederDto.cs`;
    * сущности из `TimeDbContext` — DTO в `Infrastructure.Postgres\Time\SeederDto\<Entity>SeederDto.cs`.
  * Пример для `Course` (таблица в `MainDbContext`):
    * файл: `Infrastructure.Postgres\Main\SeederDto\CourseDto.cs`

```csharp
public record CourseSeederDto(Guid Id, string Title, string? Code, string? Description, DateTime? CreatedAt, DateTime? UpdatedAt);
```
* Структура `CourseSeederDto` должна соответствовать формату JSON,
  который генерируется из Google Sheets (лист `DataModel`)
  и используется в инфраструктуре сидирования.

---

3. **Создание сидера (Seeder)**
   * Для новой таблицы создать класс-сидер на базе общего шаблона:
     ```csharp
     // общий паттерн
     <Entity>Seeder : BaseSeeder<TContext, TEntity, TDto>
     ```
  ❗ **ВАЖНО:** имя класса сидера должно строго соответствовать шаблону **`<Entity>Seeder`**, так как этот шаблон используется по умолчанию в системе обнаружения сидеров внутри инфраструктуры сидирования. Если имя будет отличаться — сидер не будет найден автоматически.

   * Пример для сущности `Course` в `MainDbContext`:
     ```csharp
     public sealed class CourseSeeder : BaseSeeder<MainDbContext, Course, CourseDto>
     {
         // реализация абстрактных методов базового сидера
     }
     ```
   * Реализовать 4 абстрактных метода:
     * как искать запись по ключу (`TryFindEntity`),
     * как создавать (`AddNewEntity`),
     * как обновлять (`UpdateEntity`),
     * как удалять все записи (`RemoveEntities`).  

      ℹ За основу можно взять любой уже реализованный сидер и просто заменить в нём тип сущности и имена полей — общая структура и логика работы всех четырёх методов остаётся одинаковой.

   * Указать **ранг (уровень)** сидера в соответствии с зависимостями (0–3).
     Для `Course` (корневая справочная таблица) — уровень `0`.  
     Более подробно смотри **[Общие подходы к организации сидирования](https://github.com/DSivtsov/SeaWind/wiki/SeedingOrganization)**.

---

4. **Регистрация сидеров в DI**
   * Для каждой сидируемой таблицы необходимо зарегистрировать соответствующий сидер через интерфейс `ISeeder<TContext>` в `Infrastructure.Postgres\DbSeedersDI.cs`.
   * Пример регистрации для сущности `Course` (MainDbContext):
```csharp
services.AddScoped<ISeeder<MainDbContext>, CourseSeeder>();
```
---

5. **Подготовка демо-данных**
* Подготовить таблицу с демо-данными в Google Sheets (на соответствующем листе `DataModel`),
  структура таблицы должна соответствовать сущности по количеству полей и их типам.
* Выделить диапазон и выполнить макрос `selectionToJson`
  (при выделении **обязательно** включать строку-шапку с названиями полей/колонок).
* Полученный JSON-файл положить в соответствующую папку `*DbContext*/SeedData/`
  и назвать в соответствии с используемым шаблоном, по умолчанию — `Demo{Entity}.seed.json`.
  Для `Course` (из `MainDbContext`):
  * файл: `DemoCourse.seed.json`
  * папка: `Infrastructure.Postgres\Main\SeedData\`

6. **Настройка `appsettings.*`:**
   * В `src/backend/Api/appsettings.Development.json` необходимо включить сидирование для нужного DbContext  
     и указать соответствующий набор параметров.  
     За основу можно использовать пример:  
     `src/backend/Api/appsettings.Development.json.example`.

   * Рекомендуется задавать параметры через **пресеты сидирования** (`Seed:Preset` в *appsettings*):  
     `SuperFast` | `Fast` | `Real`.

7. **Запуск:**
   * Запустить хост (`Api`) в любом режиме (`Debug` или `Release`).  
     По логам можно убедиться, что:
     * были применены миграции (если включено `AutoMigrate`),
     * выполнилось сидирование,
     * либо увидеть описание:
       - ошибок, из-за которых сидирование было остановлено;
       - предупреждений, с учетами которых сидирование было выполнено.

### Преимущества
* **Повторяемость** — одинаковый набор демо-данных можно поднять на любом DEV/TST окружении.
* **Идемпотентность** — повторный запуск не засоряет БД, а корректно обновляет записи по ключу.
* **Централизация** — все правила и код сидирования находятся в `Infrastructure.Postgres` и настраиваются через `src/backend/Api/appsettings*`.
* **Прозрачность** — чтобы добавить новую сущность, достаточно следовать стандартному шаблону сидера и существующей структуре каталогов.
* **Интеграция с миграциями** — можно сначала применить EF-миграции, затем автоматически выполнить сидирование.

## Out of Scope
Из этого ADR **исключены** следующие вопросы:
*   Сидирование **NoSQL-хранилищ** (MongoDB, хранилище вложений в чатах и т.д.) — будет описано отдельным решением.
*   Использование **реальных продакшен-данных** или анонимизированных копий — отдельный процесс (ENV/данные), не относится к демо-сидерам.
*   **Версионирование демо-данных** (v1/v2 файлов, миграция самих seed-файлов) — зафиксирована только текущая схема с каталогами `SeedData/`.
*   Подробная спецификация и поддержка макроса `selectionToJson` (Google Apps Script) — считается внешним инструментом и может описываться в отдельном HOWTO.
*   UI/панель управления сидированием (включение/выключение режимов из интерфейса) — по текущему решению всё управление делается через `appsettings.*`.
