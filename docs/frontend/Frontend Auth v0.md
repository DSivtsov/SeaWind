# Frontend Auth v0 — описание подхода

## Назначение документа

Этот документ описывает подход **Frontend Auth v0**, используемый в проекте **WorkshopCode** для реализации аутентификации.

---

## Область применения

Подход Frontend Auth v0 применяется ко всем экранам и страницам Frontend MVP, включая:
- публичные страницы (`/`, `/courses`);
- экраны, использующие авторизованные API;
- модальные окна Login / Registration;
- layout-уровень (`CoursesLayout`).

---

## Ключевые принципы

### MVP-first

- Реализуется **минимально достаточная** схема аутентификации.
- Исключены решения, не дающие прямой ценности на этапе MVP.
- Любое расширение требует отдельного архитектурного решения (ADR).

### Централизация ответственности

- HTTP-статусы (`401 / 403`) обрабатываются **централизованно**.
- UI-компоненты не принимают решений об аутентификации.
- Навигация при проблемах доступа выполняется в одном месте.

### Предсказуемый UX

- Приложение **никогда не выглядит «сломавшимся»**.
- Пользователь не блокируется forced-login окнами.
- Любая потеря доступа сопровождается понятным сообщением.

---

## Хранение токена (MVP)

- Используется **`localStorage`**.
- Токен также хранится в памяти для runtime-доступа UI.
- Refresh token **не используется**.
- JWT TTL фиксирован и составляет **2 часа**.

### Причины выбора

- Простота реализации.
- Переживание перезагрузки страницы.
- Возможность синхронизации logout между вкладками.
- Отсутствие необходимости в серверной сессии.

---

## Разделение ответственности

### `authStorage.ts` (infra, без React)

Ответственность:
- операции с токеном:
  - `getAccessToken`
  - `setAccessToken`
  - `clearAccessToken`
- pub/sub для событий потери доступа:
  - `emitUnauthorized(reason)`
  - `onUnauthorized(cb)`
- тип причины:
  ```ts
  type LoginReason = "unauthorized" | "forbidden";
  ```

`authStorage` **не содержит**:
- навигации;
- UI-логики;
- React-зависимостей.

---

### `apiRequests.ts` (fetch wrapper)

Ответственность:
- автоматическое добавление `Authorization: Bearer <token>`;
- обработка HTTP-статусов:
  - `401` → `emitUnauthorized("unauthorized")`
  - `403` → `emitUnauthorized("forbidden")`
- выброс ошибки для вызывающей стороны.

`apiRequests` **не выполняет**:
- навигацию;
- открытие модалок;
- изменение UI.

---

### `AuthProvider` (React)

Роль:
- единственная точка принятия решения при `401 / 403`.

Поведение:
1. Подписывается **один раз** на `onUnauthorized`.
2. При событии:
   - очищает токен;
   - сбрасывает auth‑state;
   - выполняет:
     ```ts
     navigate("/courses", {
       replace: true,
       state: { accessDenied: reason }
     });
     ```

Зависимости эффекта:
- только `navigate`;
- `token` **не используется** в `useEffect deps`.

---

### UX на `/courses`

- `CoursesLayout` читает `location.state?.accessDenied`.
- Показывается **небольшое информационное модальное окно**:
  - `unauthorized` → «Чтобы продолжить, войдите в систему»
  - `forbidden` → «У вас нет доступа к этому разделу»
- State «съедается» через `replace`, сообщение показывается **один раз**.
- Login остаётся **добровольным действием пользователя**.
