# Base Theme v0 — описание подхода (Frontend MVP)

## Назначение документа

Этот документ описывает подход **Base Theme v0**, используемый в проекте WorkshopCode
для разработки Frontend на этапе **MVP**.

Документ предназначен для:
- хранения в репозитории проекта;
- онбординга новых участников;
- предотвращения расхождений в визуальном и структурном подходе;
- сохранения архитектурного контекста без привязки к чатам и устным договорённостям.

---

## Контекст

В рамках Frontend MVP было принято осознанное решение:
- не вводить преждевременное разделение UX-режимов (public / private);
- использовать **единый базовый визуальный и UX-подход** для всех страниц MVP.

---

## Определение Base Theme v0

**Base Theme v0** — это единый базовый визуальный и UX-стиль приложения
на этапе Frontend MVP.

Он определяет:
- визуальный язык интерфейса;
- базовые UX-допущения;
- правила использования layout, CSS и компонентных стилей.

Base Theme v0 **не является**:
- финальным дизайном продукта;
- brand- или marketing-темой;
- ограничением для будущего развития UI.

---

## Область применения

Base Theme v0 применяется:
- ко всем страницам Frontend MVP;
- ко всем ролям (Guest, Student, Mentor, Admin);
- ко всем базовым layout и компонентам.

Разделение UX-режимов допускается **только в будущем** и **только при наличии реального конфликта требований**.

---

## Ключевые принципы

### 1. Единый визуальный стиль
- Один базовый визуальный язык для всего MVP.
- Отсутствие альтернативных тем и ответвлений.

### 2. Минимальная достаточность
- Используется только то, что необходимо для текущего объёма MVP.
- Любое усложнение требует явного обоснования.

### 3. Управляемость изменений
- Изменения Base Theme v0 не должны ломать существующие экраны.
- Новые паттерны вводятся осознанно и точечно.

---

## Технические правила

### CSS
- Один глобальный файл: `app.css`, отвечает только за:
  - фон,
  - layout,
  - overlay-поверхности.
- Отдельно `pages/landing/landing.css`
  - используется только для background/layout/overlay Landing,
  - в него нельзя добавлять стили компонентов (кнопки/тексты/карточки).
- Для всех **CSS** запрещено:
  - дублировать токены Mantine,
  - вводить параллельные темы,
  - стилизовать компоненты вне Mantine props.

### Компоненты
- Все UI-компоненты реализуются через Mantine.
- Стилизация осуществляется через props и theme.
- Кастомный CSS для компонентов запрещён.

---

## Layout-подход

- Layout-архитектура подчиняется SiteMap проекта.
- Используются согласованные layout-контракты:
  - Full-screen pages (Landing);
  - Layout + PageShell + Content;
  - Role-based layouts (Mentor / Admin).

Base Theme v0 не переопределяет layout-логику, а накладывается поверх неё.

---

## Scroll model (AppShell)

В Base Theme v0 используется единая модель скролла для layout на базе Mantine AppShell.

### Принципы

- Layout фиксируется по высоте viewport (`height: 100vh`).
- Header и Footer являются overlay-областями и не участвуют в скролле.
- Скролл разрешён **только внутри `AppShell.Main`**.
- Корневой контейнер AppShell использует `flex` с вертикальной колонкой
  (`header / main / footer`).

### Реализация

- `AppShell.root`
  - `height: 100vh`
  - `display: flex`
  - `flex-direction: column`

- `AppShell.Main`
  - `flex: 1`
  - `min-height: 0` — обязательно для корректной работы overflow внутри flex
  - `overflow-y: auto`

- Компенсация overlay Header/Footer:
  - `padding-top: var(--app-shell-header-offset)`
  - `padding-bottom: var(--app-shell-footer-offset)`
  - значения offset рассчитываются Mantine автоматически

### Разграничение ответственности

- Layout отвечает только за:
  - структуру,
  - скролл,
  - компенсацию header/footer.
- Контентные отступы (`padding`, `margin`) задаются **на уровне страницы**
  (Page / PageShell), а не в Layout.

### Цель подхода

- предсказуемый скролл,
- отсутствие двойного скролла,
- единое поведение для всех страниц MVP,
- отсутствие layout-зависимых хаков в контенте.

---

## Критерии возможного пересмотра

Возврат к вопросу разделения UX-режимов возможен **только если** возникнет:
- конфликт плотности интерфейса;
- конфликт поведения UI-паттернов;
- конфликт ответственности экранов.

До появления таких критериев Base Theme v0 считается достаточным и окончательным
для этапа MVP.
